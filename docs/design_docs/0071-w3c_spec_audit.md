# Design: W3C Specification Audit and Gap Closure

**Status:** Draft. The audit is complete as a source reading of revision `b39a524a2`; nothing was
built or executed, no gap has been fixed and no new suite case has been authored. The ledgers under
[`docs/spec_audit/`](../spec_audit/README.md) hold the evidence; the plan below orders the work.
**Author:** Claude Fable 5.2
**Drafted by:** Claude Fable 5.2 and Claude Opus 5.5
**Created:** 2026-11-14

## Summary

This document reports a row-by-row audit of Donner against the SVG 2 Candidate Recommendation
Snapshot of 06 October 2026 and against the latest published W3C Technical Report of each
specification SVG 2 depends on: CSS syntax, values, selectors, cascade, color, transforms, text,
fonts, writing modes, Filter Effects, CSS Masking, Compositing and Blending, XML with its companion
specifications, and the WOFF font containers. It also compares the SVG 2 feature set with the
vendored resvg test suite to find features that no portable test exercises.

The audit is inventory driven. Every element in the CR element index, every row of the CR attribute
index, every property in the CR property index and every property the styling chapter requires has a
matrix row, as does every keyword or grammar alternative of each property. For each dependent
specification a feature inventory was derived from its own text (productions, algorithms, value
definitions, numbered rules) and each inventory item has a row. Each row records the specification
anchor, the requirement, the Donner code that parses it, the Donner code that consumes it, the tests
that assert it, and a class.

Everything in this document is the result of reading source at revision `b39a524a2` and reading the
dated specification text. No code was built and no test was run. A behavioral claim is a
code-reading result until a test confirms it.

The matrix has 4,140 rows in 17 ledgers:

| Class                 | Rows  | Meaning                                                                |
| --------------------- | ----- | ---------------------------------------------------------------------- |
| `conformant`          | 1,758 | The code was read and a named test asserts the behavior.               |
| `conformant-untested` | 345   | The code was read and matches; no test asserts it.                     |
| `partial`             | 547   | Implemented with named missing values, cases or sub-features.          |
| `divergent`           | 220   | Implemented, and behaves differently from the specification.           |
| `missing`             | 829   | Not implemented.                                                       |
| `not-applicable`      | 363   | Outside what a script-free XML renderer must do, with a stated reason. |
| `spec-ambiguity`      | 45    | The text is unclear, or two normative texts conflict.                  |
| `legacy`              | 33    | Donner implements something the CR or the dependent TR removed.        |

These counts are not a conformance percentage;
[Audit Totals and How to Read Them](#audit-totals-and-how-to-read-them) explains why. Of the 1,596
`partial`, `divergent` and `missing` rows, 35 are rated high impact, 208 medium and 1,353 low. The
35 high rows describe 13 distinct defects.

The findings that matter most:

- **Inheritance compares cascade priority across elements.** A child's own declaration of an
  inherited property is replaced by its parent's value whenever the parent's declaration has a
  strictly higher specificity, for example a parent `style` attribute against a child presentation
  attribute. Nine properties carry a repair; 35 inherited properties do not.
- **Ordinary files fail to load.** Any processing instruction whose target starts with `xml`,
  including `<?xml-stylesheet?>`, is parsed as the XML declaration and fails the document. The
  1,001st character or predefined entity reference is a fatal error. A pretty-printed file with
  about 4,095 elements exceeds the default node limit. A custom entity reference with 64 KiB or more
  of document after it is silently left unexpanded.
- **`color: hsl(...)` aborts the process.** The computed `color` keeps its HSL form and every drawn
  element that inherits it reads it through an accessor that assumes RGB. This is a known defect
  with a fix in review.
- **Transforms pivot about the wrong point or compose in the wrong order.** CSS `transform` lists
  reverse runs of adjacent non-translate functions. The transform reference box is offset by the
  `viewBox` origin, so `rotate(45)` inside `viewBox="100 100 200 200"` pivots about (100,100). On
  `use` and nested `svg`, `x` and `y` act as the pivot of the element's own transform.
- **The CSS engine has no conditional rules, custom properties or math.** `@media` and `@supports`
  blocks are dropped whole, including `@media all`; `var()` and `calc()` invalidate the declaration;
  `:hover`, `:link`, `:focus` and `:lang()` invalidate the whole rule.
- **Cascade order has two defects that affect static rendering.** Several `style` elements apply in
  reverse document order, and a selector list takes the specificity of its first matching member
  instead of its most specific one.
- **Bidirectional text is reordered only in part of the layout space.** Wrapped text, text on a
  path, text with preserved line breaks and upright vertical text get no UAX #9 reordering.

Core static rendering is otherwise in good shape. Path data, basic shapes, the `transform` attribute
grammar, `viewBox` and `preserveAspectRatio`, fills, strokes, all sixteen blend modes, `clipPath`,
`mask` elements, gradients, patterns, markers and every filter primitive are implemented on both
renderers and run against the resvg suite, with the edge-case gaps listed per area below.

## Goals

- Record, for every element, attribute, property, value and feature of the SVG 2 CR of 06 October
  2026 and of the latest published version of each dependent specification, whether Donner conforms,
  with source evidence for both the parse step and the consuming step.
- Separate the kinds of finding: missing implementation, partial implementation, divergent behavior,
  conformant code with no asserting test, specification ambiguity, and legacy behavior.
- Record where the two renderers (the CPU renderer and the Geode GPU renderer) or the two text
  backends (the basic backend and the HarfBuzz backend) disagree with each other.
- List the SVG 2 behaviors that the resvg suite does not assert, and name the cases to author for
  the Donner SVG suite described in [0057](0057-donner_svg2_test_suite.md).
- Turn the findings into ordered work items with engineer-day ranges, so each milestone can become
  its own implementation slice.

## Non-Goals

- Fixing any gap in this change. Every milestone is a later slice with its own tests and review.
- Executed conformance results. Each behavioral claim is a code-reading result. Rows that could not
  be settled by reading are listed in each ledger's "Unverified" section.
- A conformance percentage. Row counts measure how finely a specification was itemized, not how much
  of it Donner implements.
- Auditing Editor's Drafts. Dependent specifications are read at their latest published Technical
  Report. SVG Animations Level 2 has no published TR, so its Editor's Draft was read and those rows
  carry draft status.
- Script execution, the SVG DOM as Web IDL, HTML rendering inside `foreignObject`, and platform
  accessibility APIs. Donner is an XML-only renderer without a script engine or an HTML layout
  engine. These have `not-applicable` rows that name the C++ counterpart where one exists.
- Replacing [`docs/svg2_audit.md`](../svg2_audit.md). That ledger tracks requirement-level test
  evidence against the Editor's Draft. This audit is an inventory against the published CR and its
  dependencies.

## Next Steps

- Decide the items under [Open Questions](#open-questions) that gate Milestone 1 and Milestone 2:
  the default XML limits, whether `gradientTransform` and `patternTransform` inherit through `href`,
  and the invalid presentation attribute rule.
- Start Milestone 1. For each item write the failing test first, on both renderers where the defect
  is in rendering, then fix it and update the ledger rows listed for the item.
- Start Milestone 3 in parallel: author the P1 suite cases so later milestones have portable tests
  to turn green.

of matrix rows. They are not sums of the per-row sizes in the ledgers: a missing property
contributes one row per value, and one parser fix can close thirty rows. Ranges include the tests
and the ledger update. They are planning numbers, not commitments. An item that closes matrix rows
lists their keys; a key ending in `*` is a prefix. Milestone 3 items author tests and close no rows,
so they cite TC and RC identifiers instead. An item that waits on a decision or tracks a change in
review has no range and says so.

## Background

Three existing documents overlap this one. [0057](0057-donner_svg2_test_suite.md) owns the Donner
SVG suite and the requirement-level ledger in `docs/svg2_audit.md`, which targets the SVG Working
Group Editor's Draft. [0058](0058-svg_static_subset_roadmap.md) inventories what remains for the
static subset from the resvg run. [0062](0062-svg_parity_completion.md) is the active completion
program for paint, text, clip and mask parity. [0069](0069-bidi_text_layout.md) is the bidi design
that Milestone 8 continues.

This audit adds three things those documents do not have: the published CR as the baseline, the
dependent specifications at their latest published level, and a row for every inventory item instead
of a row for every known problem.

## Audit Method

**Inventory.** For SVG 2, the inventory is the CR's own indexes: all 63 elements of the element
index (`el:` keys), every row of the attribute index (`attr:` keys, 331 rows), every property of the
property index and every property the styling chapter requires (`prop:` keys, 190 rows), and each
keyword or grammar alternative of each attribute and property (`val:` keys, 1,228 rows). Prose rules
and algorithms of each chapter are feature rows (`feat:svg2/...`). For each dependent specification
the inventory is derived from that specification: grammar productions, numbered algorithms, value
definition tables and normative sentences each become a feature row keyed by the specification's
short name (2,328 `feat:` rows in all). Each ledger has an "Inventory" section that states the
derivation and lists the keys, so a missing row is detectable.

**Evidence standard.** A row cites the parse site and the consuming site as `path:line` at revision
`b39a524a2`. A property that parses and has no consumer is not conformant.

| Class                 | Evidence required                                                                                     |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| `conformant`          | The implementing lines were read against the requirement and a named test or resvg case asserts it.   |
| `conformant-untested` | The implementing lines were read against the requirement. No test asserts it.                         |
| `partial`             | The row names what works and what does not, each with evidence.                                       |
| `divergent`           | The row cites the lines that produce the different behavior and, where one fits, a minimal example.   |
| `missing`             | The row cites the search that found no implementation, or the line that rejects the input.            |
| `not-applicable`      | The row states why a script-free XML renderer has no such requirement, and names the C++ counterpart. |
| `spec-ambiguity`      | The row quotes or paraphrases the conflicting or silent text and states what Donner does.             |
| `legacy`              | The row cites the specification text that removed the feature and the Donner code that keeps it.      |

**Independent re-read.** An independent re-read of the source tried to refute every non-conformant
row rated high and a list of 40 named medium and low claims. All 13 distinct high-impact defects
hold as the ledgers state them. The headline tables mark each row the re-read covered as confirmed
and each row it did not cover as not covered. The same re-read sampled 42 rows classed `conformant`:
2 were not conformant and 2 named a test that does not assert the behavior.

**Limits.**

- Nothing was executed. Every example outcome in this document and in the ledgers is derived from
  the cited lines.
- The sample puts the rate of `conformant` rows that are not actually conformant at about 5 percent
  (2 of 42), and the rate of rows whose named test does not assert the behavior at about 5 percent
  more. The 1,758 `conformant` total should be read with that error rate: outside the sample, the
  class was read once.
- Test evidence is a named test read far enough to see what it asserts. For resvg cases it is the
  registration in `donner/svg/renderer/tests/resvg_test_suite.cc` (compared, thresholded,
  render-only or skipped), not an observed pass.
- Parts not read in depth, collected from the ledgers' "Unverified" sections:
  - Geode shader math for the blend, composite, color matrix, component transfer and displacement
    programs was not read line by line; Geode evidence for those rows is the dispatch and parameter
    code ([filters_core](../spec_audit/filters_core.md)). The independent re-read of the turbulence
    and lighting rows covered the CPU path only.
  - The JFIF document was not fetched, so the JPEG requirement rows are not backed by its text
    ([color_compositing](../spec_audit/color_compositing.md)).
  - The SMIL interval pseudo-code was not compared line by line with the timeline code, and the
    base-value and path-value animation sources were read at the function level only
    ([animation](../spec_audit/animation.md)).
  - The vendored CPU stroker's join and cap geometry was not traced
    ([painting_properties](../spec_audit/painting_properties.md)).
  - [text_layout](../spec_audit/text_layout.md) read only the SVG 2 text chapter; the dependent CSS
    text specifications are audited in
    [text_font_properties](../spec_audit/text_font_properties.md). The OpenType specification was
    used for table names only.
  - RFC 1952, RFC 3986, RFC 3987, RFC 7303 and the URL and Fetch standards were not fetched;

    general knowledge.

### Reference conflicts

The upstream resvg fixture stays unchanged in each case, and a Donner case with a cited rationale is
needed. Details are in the coverage ledger.

- **RC1.** `painting/stroke-linejoin/miter-clip.svg` shows the clipped miter. The CR removed

  removed value (`val:stroke-linejoin/miter-clip` in

- **RC2.** The two `non-presentational-attribute.svg` cases expect SVG 1.1 to ignore `height` in
  `style`. In the CR it is a CSS property.
- **RC3.** `painting/fill/rgb-int-int-int.svg` marks space-separated `rgb()` as undefined. The CR's
  normative color reference is CSS Color 3; Donner accepts the modern form (`val:color/rgb()-modern`
  in [color_compositing](../spec_audit/color_compositing.md)).
- **RC4.** `paint-servers/radialGradient/fr=0.7.svg` paints a reversed gradient where Donner paints
  nothing (`feat:svg2/radial-start-circle-contains-end-circle` in
  [paint_servers_markers_images](../spec_audit/paint_servers_markers_images.md)).
- **RC5.** Paint server bounding boxes on text use glyph ink extents in the references and glyph
  cells in Donner (`feat:svg2/text-bbox-glyph-cells` in
  [text_layout](../spec_audit/text_layout.md)).
- **RC6.** Several skips and thresholds cite an opaque white reference background against Donner's
  transparent canvas. Both renderers return a transparent canvas, and the pixel comparison uses
  straight-alpha output against transparent-background references with no flattening, so the suite
  exercises only the embedded case and no test can detect a white backdrop either way. The CR

  let the affected cases compare was not established; each needs its own look.

  identical to the `align` reference.
- **RC9.** Four `drop-shadow()` references truncate fractional device offsets that Donner

## Proposed Architecture

The audit introduces no runtime architecture. It adds documentation:

- This design document, which carries the summary, the baseline and the plan.
- Seventeen implementation ledgers and the coverage ledger under `docs/spec_audit/`, indexed by
  [`docs/spec_audit/README.md`](../spec_audit/README.md). Each implementation ledger has a "Specs
  read" table with dated URLs, an "Inventory" section, the matrix, "Tests to create" and
  "Unverified" sections.
- `docs/spec_audit/matrix.tsv`, one line per matrix row with ledger, key, class, impact, size and
  whether a test exists. The numbers in this document were computed from it at the time of writing
  and can be recomputed from it.

A row is identified by its ledger and key. Keys have a kind prefix: `el:` element, `attr:` attribute
(with `@element` where the row is element specific), `prop:` property, `val:` value of an attribute
or property, `feat:` feature, with the specification short name after the colon. A fix cites the
keys it closes, adds or names the test that proves the behavior, and updates the ledger rows and
`matrix.tsv` in the same change.

Three cross-cutting observations shape the plan:

- **Shared value parsers.** Several findings are one defect seen from different properties: the
  reference parser behind `marker-*` and `mask`, the `href` setters that ignore precedence, and the
  length resolution paths that pass default font metrics. Fixing the shared helper closes each
  group.
- **A computed-value stage.** `var()`, `calc()` with percentages, relative units and color functions
  all need values that stay symbolic until computed-value time. Donner parses most properties
  straight to final typed values. Milestone 4 should design that stage once instead of per feature.
- **Cascade as a sort.** Declarations are folded in application order with a priority comparison
  (`feat:css-cascade-4/value-stage-cascaded` in
  [selectors_cascade](../spec_audit/selectors_cascade.md)). That is equivalent to the cascade sort
  for one `style` element and is the common cause of the sheet-order, selector-list and inheritance
  defects. Layers need a real ordering key in any case.

## Security / Privacy

SVG, CSS, fonts and images are untrusted input. The audit touches the trust boundary in these ways.

- **Content-triggered process abort.** `color: hsl(...)` on any ancestor of a drawn element
  terminates the process (`feat:css-color-4/color-property-hsl-storage` in
  [color_compositing](../spec_audit/color_compositing.md)). A fix is in review. The same ledger
  records two residual paths where an unresolved color can reach an accessor that asserts, with
  reachability unverified (`feat:css-color-4/non-rgba-storage-paths`). The fix needs a regression
  test on both renderers and fuzzer coverage for non-RGB computed colors.
- **Parser limits that reject legitimate input.** The entity byte budget, the reference count and
  the node count (`feat:xml/limit-entity-expansion-bytes`,
  `feat:xml/limit-entity-substitution-count`, `feat:xml/limit-tree-nodes` in
  [xml_data_formats](../spec_audit/xml_data_formats.md)) are security bounds whose current form
  fails closed on ordinary files. The fixes must keep the amplification bound: measure expanded
  output, count only references that can amplify, and keep a node ceiling that a caller can raise.
  The entity depth bound and the inflation cap for compressed input are recorded as intentional and
  conformant (`feat:xml/limit-entity-depth`, `feat:svgz/gzip-detection-and-decoding`).
- **External entities and external resources.** External entities are never fetched, which is the
  right posture; the gap is only that the reference text appears in output with no warning
  (`feat:xml/entity-external-not-fetched`, `feat:xml/wfc-NoExternalRefs` in
  [xml_data_formats](../spec_audit/xml_data_formats.md)). SVG documents used as images are parsed in
  secure static mode with external loads disabled (`feat:svg2/image-svg-secure-mode` in
  [paint_servers_markers_images](../spec_audit/paint_servers_markers_images.md)). Loading
  `xml-stylesheet` targets, `link` style sheets, `local()` fonts and external paint server templates
  (Milestones 5 and 8) must go through the existing resource-loading policy; `local()` also exposes
  installed fonts and needs an explicit host opt-in.
- **Parser differentials.** Donner accepts documents that XML requires rejecting, and some render
  with different content than in a conforming parser: duplicate attributes, undeclared entities kept
  as text, an entity value that splits an element (`feat:xml/error-recovery-policy`,
  `feat:xml/wfc-uniqattspec`, `feat:xml/entity-wellformed-replacement` in
  [xml_data_formats](../spec_audit/xml_data_formats.md)). A file that a sanitizer and Donner parse
  differently is a risk for hosts that filter SVG before rendering it.
- **Limits must fail visibly.** Where a resource limit makes content disappear
  (`feat:filter-effects-1/implementation-limits` in [filters_core](../spec_audit/filters_core.md))
  or differ between renderers (the gradient stop limit, the dash limits, the blend fallback in
  [Renderer and Backend Disagreements](#renderer-and-backend-disagreements)), the replacement
  behavior should be defined, tested and reported through the existing diagnostics.
- **New features widen the attack surface.** `var()` substitution needs cycle detection and an
  expansion bound. Math functions need depth limits. UTF-16 decoding and stricter well-formedness
  checks run before any other validation and need fuzzing. View fragments and media fragments are
  attacker-controlled strings parsed from URLs.

## Testing and Validation

- Every fix lands with a test that fails before it. For a divergent row the test states the
  specified behavior and cites the anchor; the ledger's "Tests to create" item gives the minimal
  content.
- Rendering fixes are asserted on both renderers. A fix for a row in
  [Renderer and Backend Disagreements](#renderer-and-backend-disagreements) is not complete until
  both agree with the specification, and text fixes name the backend they cover.
- The tests in [Tests That Pin Non-Conformant Behavior](#tests-that-pin-non-conformant-behavior)
  change with the fix, and the change description says so.
- Rows established only by reading a multi-step path (the ledgers mark them "by code reading") get
  the confirming test first. If the test passes, the ledger row is corrected instead of the code.
- Renderer behavior is asserted through the Donner SVG suite cases listed above in addition to the
  resvg suite in `donner/svg/renderer/tests/resvg_test_suite.cc`. Skips and thresholds in that file
  are removed only after the focused case passes.
- Parser changes extend the existing CSS and XML fuzzers. The vendored CSS parsing corpus predates
  the current CSS Syntax text (`feat:css-syntax-3/ident-non-ascii-code-points` in
  [css_syntax_values](../spec_audit/css_syntax_values.md)), so a newer snapshot is needed before the
  block-parsing work.
- The `conformant-untested` rows are closed by adding the asserting test, not by changing code.
  Given the sampled error rate, some of those tests will fail and convert the row to a finding.

## Open Questions

Decisions the ledgers surface for the maintainer:

- **Invalid presentation attributes.** Follow the CR (the initial value applies and blocks
  inheritance) or keep ignoring the attribute, as the ledgers understand browsers to do? The ledgers
  rate the gap medium in [styling_properties](../spec_audit/styling_properties.md)
  (`feat:svg2/styling-presattr-invalid-value-initial`) and low in
  [painting_properties](../spec_audit/painting_properties.md)
  (`feat:svg2/painting-presentation-attribute-invalid-value`) and
  [css_syntax_values](../spec_audit/css_syntax_values.md)
  (`feat:svg2-types/invalid-presentation-attr-as-initial`).
- **Hidden content in clip paths.** Follow SVG 2 (a hidden element contributes) or CSS Masking (it
  does not), and make the `use` case consistent either way
  (`feat:svg2-render/visibility-hidden-in-clip` in
  [clipping_masking](../spec_audit/clipping_masking.md))?
- **Turbulence gradient setup.** Keep the SVG 1.1 form that the existing reference images and the
  resvg references encode, or follow the 2018 text, which changes all turbulence output
  (`feat:filter-effects-1/turbulence-gradient-setup` in
  [filters_generators_lighting](../spec_audit/filters_generators_lighting.md))?
- **`gradientTransform` and `patternTransform` through `href`.** A code comment documents the
  current behavior as intended; the CR lists both among the copied attributes
  (`feat:svg2/gradient-href-gradientTransform` in
  [paint_servers_markers_images](../spec_audit/paint_servers_markers_images.md)). Which holds?
- **Default XML limits.** What should the default node ceiling be, should white-space text nodes
  count, and should the entity limits be configurable per host (`feat:xml/limit-tree-nodes` in
  [xml_data_formats](../spec_audit/xml_data_formats.md))?
- **XML strictness.** Should well-formedness violations become fatal as XML requires, stay lenient,
  or be reported as warnings (`feat:xml/error-recovery-policy` in
  [xml_data_formats](../spec_audit/xml_data_formats.md))?
- **White backdrop.** Should standalone output (the command-line tool writing an image) composite
  onto opaque white, with the library API keeping a transparent canvas
  (`feat:svg2-render/standalone-document-white-backdrop` in
  [color_compositing](../spec_audit/color_compositing.md))?
- **Default document size.** Keep the documented default of 512 or use the 300 by 150 default object
  size (`feat:svg2/coords-default-object-size-300x150` in
  [transforms_coordinates](../spec_audit/transforms_coordinates.md))?
- **Media query environment.** Which viewport and media type does a headless render evaluate
  `@media` against, and how does a host supply them (`feat:mediaqueries-4/viewport-for-svg` in
  [css_syntax_values](../spec_audit/css_syntax_values.md))?
- **`switch` selection.** Keep the normative reorder rule or follow first match as browsers do
  (`feat:svg2/switch-allowreorder-language-priority` in [structure](../spec_audit/structure.md))?
  Should `foreignObject` take part in selection (`feat:svg2/switch-eligible-children`)?
- **SVG 1.1 behaviors the resvg references encode.** `transform` on `symbol`
  (`feat:svg2/symbol-transform` in [structure](../spec_audit/structure.md)), marker orientation on
  closed subpaths (`feat:svg2/marker-orient-closed-subpath` in
  [paint_servers_markers_images](../spec_audit/paint_servers_markers_images.md)) and the legacy
  keywords in the legacy table: follow the CR and add Donner cases, or keep the reference behavior?
- **Removed joins.** Do `miter-clip` and `arcs` stay as documented extensions
  (`val:stroke-linejoin/miter-clip` in [painting_properties](../spec_audit/painting_properties.md))?
- **Nested `svg` isolation.** Follow the CR (always an isolated group) or Compositing 1
  (`feat:svg2-render/svg-element-is-isolated-group` in
  [color_compositing](../spec_audit/color_compositing.md))?
- **SVG images in an animated host.** Should an SVG used as an image animate in secure animated mode
  (`feat:svg2/referencing-mode-image` in [structure](../spec_audit/structure.md))?
- **The basic text backend.** Should it render document-supplied fonts and shape complex scripts, or
  are those documented limits of that backend (`feat:svg2/text-font-fallback` in
  [text_layout](../spec_audit/text_layout.md))?
- **Scope decisions.** Is `BackgroundImage` in scope (`val:in/BackgroundImage` in
  [filters_core](../spec_audit/filters_core.md))? `foreignObject` beyond an element type
  (`el:foreignObject` in [structure](../spec_audit/structure.md))? `mask-border` (`prop:mask-border`
  in [clipping_masking](../spec_audit/clipping_masking.md))? CSS Color 5 while it is a Working
  Draft? An accessibility tree export?
- **Filter limits.** What should an over-limit filter do in place of hiding the element: render
  unfiltered, clamp, or report an error (`feat:filter-effects-1/implementation-limits` in
  [filters_core](../spec_audit/filters_core.md))?
- **Two baselines.** How should this audit and `docs/svg2_audit.md` share one baseline once the CR
  and the Editor's Draft diverge further?
